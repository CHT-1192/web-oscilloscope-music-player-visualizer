# 网页版示波器音乐播放 / 可视化器

左声道 → X 轴，右声道 → Y 轴。用电子束轨迹画出利萨如图形和示波器音乐里的矢量画面。

![预览](docs/preview.png)

> `oscillofun.flac` @ 20s —— **描边型**曲子的参数：窗口 1024、余辉 16%、增益 1.45。
> 余辉压低才看得到真正的束径，而不是拖尾叠加出来的一团糊。

**两个硬性要求：没有回扫线，没有辉光。** 两条都是量出来的，不是嘴上保证：

- **回扫线** —— 往分析器里塞一个合成信号（慢速画方块 + 快速斜穿一条回扫线），
  方块中心的像素只可能来自那条回扫线，于是直接量像素：关闭消隐 alpha=**250**，
  开启后 alpha=**2**。原理是速度消隐：亮度 ∝ 1/束速，比平均束速快过阈值（默认 10×，
  可在设置里调 3–30×）的段落**直接不画**（只调暗没用 —— 余辉累加几十帧照样会浮出来）。
- **辉光** —— 不用 `shadowBlur`、不用叠加混合、不用模糊滤镜；余辉走 `destination-out`
  只做减法衰减，像素只会变暗，不会把亮度渗给邻居。测试里给这几个 API 装了 setter
  探针，跑完整轮播放后断言全为 0。

## 操作

拖音频文件进窗口即可播放。

![界面](docs/ui.png)

布局的原则是**画布不动，只有绘图区让位**：

- 画布（背景、网格、画布本身）永远占满窗口，开关面板**不会改变它的尺寸或位置**。
- 面板是浮层，落在正方形绘图区两侧的留白里。正方形居中，所以宽屏下两侧留白很宽
  —— 1600×900 时两侧各有约 400px，一个 330px 的面板整个塞得进去，**绘图区一动不动**。
- 只有当留白真的塞不下时（比如小窗口双开），绘图区才缩小，而且保持居中，不会被推向
  一边。窄屏（≤900px）没有余量，退回浮层覆盖。

切面板时会用 `layout()` 重新算绘图区，配合前面说的图层跨缩放保留，画面不会丢。

| 键 | 作用 | 键 | 作用 |
|---|---|---|---|
| `空格` | 播放 / 暂停 | `D` | 演示信号（不需要音频文件） |
| `←` `→` | 后退 / 前进 5 秒 | `F` / `S` | 全屏 / 存 PNG |
| `↑` `↓` | 音量 | `L` / `P` | 播放列表 / 显示设置 |
| `,` `.` | 上一首 / 下一首 | `O` | 性能模式开关 |
| `B` `T` `G` | 速度消隐 / 相位锁定 / 网格 | `R` | 恢复默认设置 |

### 参数跟着曲子走，没有通用最优

描边型和填充型的要求正好相反：

| | 采样窗口 | 余辉 | 线宽 | |
|---|---|---|---|---|
| **描边型** · `oscillofun.flac` | **1024** | **16%** | 1.15 | 就是上面那张预览图 |
| **填充型** · `primer-final.flac` | **4096** | **32%** | **2.3** | ↓ |

![填充型：primer-final.flac @ 2:43 —— 棋盘格球体，整曲的核心符号](docs/preview-primer.png)

![同一首曲子 @ 1:12 —— 放射状的「穿梭」效果](docs/preview-warp.png)

判断方法：**这首曲子在画线，还是在画面？**

- **画线**的（Oscillofun）压低余辉、缩小窗口，让真正的束径露出来；
- **画面**的（Primer）反过来 —— 用窗口和余辉把面积堆实，线宽也得跟上。

回扫阈值也是按曲调参的：不同曲子的回扫速度不一样，阈值太大回扫消不干净，太小又会
削到有效笔画（默认 10×）。它跟「速度消隐」是配套的，开关关掉时这个滑块会置灰。

同一段 Primer 换参数就能看出这不是玄学：描边配方（1024/16%）会让球体碎成几段
轮廓，默认的 62% 余辉又会堆积过头、边缘飞出杂线；只有中间这一档是干净的实心球体。

另有两个默认关闭的滑块：

- **烧屏**（独立的一层）：束流曝光的累积残影，衰减比余辉慢约两个数量级，100% 为永久。
  因为画的仍然是清晰的束径、只是记得久，所以**不违反「无辉光」**。
- **残留**：修的是余辉自己的一个量化坑。`destination-out` 是 `n ← n×(1-a)`，8 位画布
  四舍五入，于是 **n ≤ 1/(2a) 全是死点，永远降不下去**。所以余辉拉高不是"留得更久"，
  而是**残影更亮**（100% 时地板是 alpha 15，整片扫过的区域永久留下约 16% 的淡痕）。
  这个滑块控制擦除力度：0 = 定期彻底擦掉（默认，无残留），越大留得越明显。

余辉和烧屏的累积都会**跨曲目保留**，也会在窗口缩放 / 全屏切换后按比例保留
（重设 `canvas.width` 会清空位图，所以要手动搬过去，否则改一下窗口大小残影就没了）。

## 两个不那么显然的设计

**① 采样率不重采样。** Web Audio 图只有一个采样率，默认等于**设备**采样率
（一般 48 kHz），媒体元素会把音频重采样进去 —— 192 kHz 的文件就这么被砍到 24 kHz
以下。所以本项目默认让引擎跟随音频文件本身的采样率，分析器拿到的是**文件原始采样点**：
拿一份独立的 ffmpeg 解码结果逐采样比对，最大差值 `0`（逐位相同）；强制切到 48 kHz
后同段残差 −42 dB。顶栏徽标随时显示当前是「原生」还是「重采样」。

**② 性能瓶颈不在像素上。** 单帧开销几乎全在**要画多少条线段**，跟分辨率关系不大。
渲染循环用一遍扫描同时完成映射、扫峰值、算段长、分亮度档，而不是每个亮度档再全扫一遍。
实测：窗口 32768 → 1024 把单帧从 **1.49 ms 降到 0.08 ms**；「渲染缩放 50%」
反而略慢（同样的路径挤进更少的像素，单位像素覆盖更密）。弱机按 `O` 开性能模式。

其余细节都在代码里：`public/app.js` 和 `test/bench.js` 顶部都有大段注释说明。

## 几句实话

- **单文件版在 `file://` 下不能自动列目录** —— 浏览器安全限制，拖进去或点「选择文件」。
- **FLAC 播不了**说明该浏览器缺解码器，先转 WAV。
- 270 MB 的 FLAC 不会卡：走 `<audio>` 流式解码 + 服务器 Range，不整文件进内存
  （`decodeAudioData` 才会吃掉上 GB）。
- 「余辉」拉到 0 会闪（每帧全清，只画一个片段），40% 以上才累积得出完整画面。
