# 网页版示波器音乐播放 / 可视化器

把立体声音频当成示波器的 X/Y 输入：**左声道 → X 轴，右声道 → Y 轴**，用电子束轨迹
画出利萨如图形和示波器音乐（oscilloscope music）的矢量画面。

> **按需求实现的两个硬性约束：**
> **① 没有回扫线 ② 没有辉光。**
> 具体做法见下方 [「无回扫线」与「无辉光」是怎么做到的](#无回扫线与无辉光是怎么做到的)。

---

## 两个版本

| | Node.js 服务器版 | 单文件自包含 HTML 版 |
|---|---|---|
| 入口 | `server.js` + `public/` | `oscilloscope-standalone.html` |
| 启动 | `node server.js` | 双击打开 / 拖进浏览器 |
| 音频来源 | 自动列出项目目录里的音频 + 拖拽 + 选择文件 | 拖拽 + 选择文件（`file://` 下无法读目录） |
| 播放列表 | ✅ 自动生成，带时长/采样率/位深 | 手动添加 |
| 体积 | — | 单个 HTML，约 **60 KB**，零外部请求 |
| 适用 | 日常使用、局域网共享、大文件流式播放 | 拷给别人、离线演示、当附件发 |

两个版本共用同一套渲染与播放内核（`public/app.js`），单文件版由
`build-standalone.js` 把 CSS/JS 内联生成，改完源码重新生成即可：

```bash
node build-standalone.js
```

## 快速开始

### 方式一：Node 服务器版（推荐）

**零依赖**，不需要 `npm install`：

```bash
node server.js            # 打开 http://127.0.0.1:8080
node server.js --open     # 顺便自动打开浏览器
node server.js -p 3000    # 换端口（端口被占用会自动 +1 重试）
node server.js --host 0.0.0.0   # 局域网访问，会打印 LAN 地址
```

启动后终端会列出扫描到的曲目：

```
◉ WEB OSCILLOSCOPE MUSIC PLAYER — Node.js server
  app        http://127.0.0.1:8080/
  standalone http://127.0.0.1:8080/standalone   (single self-contained HTML)
  playlist   2 track(s)
              · oscillofun.flac      FLAC · 44.1 kHz · 16-bit · stereo · 2:26 · 15 MB
              · primer-final.flac    FLAC · 192 kHz · 24-bit · stereo · 5:56 · 270 MB
```

也可以 `npm start`（等价于 `node server.js --open`）。

服务器会读取音频文件头（WAV 的 `fmt `/`data`、FLAC 的 STREAMINFO），所以播放列表里的
采样率 / 位深 / 时长是**不解码**就算出来的。

### 方式二：单文件自包含 HTML 版

直接双击 `oscilloscope-standalone.html`，然后把音频文件拖进窗口，
或点「选择文件」。整个文件不依赖任何外部资源，可以随便拷走。

> `file://` 协议下浏览器不允许网页读取本地目录，所以单文件版不会自动列出音频文件。
> 如果把它放到项目目录里、再用 `node server.js` 通过 `/standalone` 访问，
> 它同样会自动读取曲目列表。

## 功能

**播放**
- 播放 / 暂停、上一首 / 下一首、进度拖动、音量、播放速度（0.25×–2×，变调保持）
- 播放列表：服务器版自动扫描项目目录，也可随时拖入本地文件
- 拖拽文件到窗口任意位置即可播放

**显示**
- X / Y 独立增益（0.1×–4×）与直流偏移
- 采样窗口 512 – 32768 个采样点（同时显示等价时长）
- 亮度、线宽、余辉（0–100%）、颜色（6 个预设 + 自定义取色器）
- **引擎采样率**：默认跟随音频文件原生采样率，不重采样（见下文），顶栏有徽标提示
- 速度消隐、相位锁定、自动增益、网格、光点，均可开关
- 内置**演示信号**（3:2 利萨如曲线），没有音频文件也能调参
- **性能模式**一键预设、渲染缩放自适应
- 全屏、画面导出 PNG

**快捷键**

| 键 | 作用 | 键 | 作用 |
|---|---|---|---|
| `空格` / `K` | 播放 / 暂停 | `D` | 演示信号 |
| `←` / `→` | 后退 / 前进 5 秒 | `F` | 全屏 |
| `↑` / `↓` | 音量 ±5% | `S` | 保存 PNG |
| `,` / `.` | 上一首 / 下一首 | `L` / `P` | 播放列表 / 显示设置 |
| `B` | 速度消隐 | `T` | 相位锁定 |
| `G` | 网格 | `R` | 恢复默认设置 |
| `O` | 性能模式开关 | `Esc` | 关闭面板 |

## 「无回扫线」与「无辉光」是怎么做到的

### 一、无回扫线

回扫线（return trace / retrace）指电子束从一次扫描终点**直线拉回**起点时留下的那条
横贯画面的亮线。这里从三个层面同时消除它：

1. **路径永不闭合。** 轨迹只 `moveTo` + `lineTo`，从不调用 `closePath()`，
   所以不会有「终点 → 起点」的收尾弦线。测试里会拦截 `closePath`，断言调用次数为 0。

2. **跨帧不连线。** 每帧都以新的 `beginPath()` / `moveTo()` 开头，上一帧的最后一点
   和这一帧的第一点之间永远不会被连起来，因此不会出现帧与帧之间的横贯跳跃。
   余辉是把上一帧**保留**在画布上，而不是把两帧连起来。

3. **速度消隐（关键）。** 亮度 ∝ 1/束速 —— 这是真实示波管的物理特性：单位长度上
   沉积的电荷是恒定的，束跑得越快，单位长度就越暗。回扫段的速度通常比正常描迹快
   一个数量级，因此：
   - 比平均束速快 1–10 倍的段落**按比例变暗**（10 级亮度分档）；
   - 比平均束速快 **10 倍以上**的段落**直接不绘制**。

   为什么要「直接不绘制」而不是「画得很暗」：在余辉模式下，即使每帧只有 4%
   的不透明度，几十帧累加之后那条线还是会重新浮现出来。所以最快的分档必须彻底
   剔除，回扫线才会真正消失。

   这个阈值是**自适应**的（以每帧平滑后的平均束速为基准），所以无论窗口大小、
   音乐快慢、增益高低都成立。

效果对比（真实文件，关闭 / 开启速度消隐）：

| 速度消隐关 | 速度消隐开 |
|---|---|
| 图形外圈那些**放射状长直线**就是回扫 | 长直线消失，画面只剩真正描出的图形 |

实测：开启后仍保留 **97% 的发光像素**，也就是只削掉了那些快速拉伸的线段，
没有破坏有效画面。（`test/shots/ab-real-blast-{on,off}.png`）

### 二、无辉光

辉光（bloom / glow）是亮线周围泛出的一圈光晕。这里从渲染管线的每一环都禁掉：

- **不用 `shadowBlur` / `shadowColor`** —— 这是 Canvas 里最典型的发光来源；
- **不用叠加混合** —— 从不设置 `globalCompositeOperation = 'lighter'`，
  像素之间不会互相加亮；
- **不用任何模糊滤镜** —— 画布上没有 `filter: blur()` / `drop-shadow()`；
- **余辉只做减法** —— 衰减用 `destination-out` 擦除 alpha，像素只会越来越暗，
  绝不可能把亮度渗到相邻像素上；
- **背景的暗角只压暗边缘**，没有任何「中心发亮」的处理；
- **线条是实心描边**，抗锯齿边缘自然收束，没有外扩的光晕。

测试里给 `CanvasRenderingContext2D.prototype` 的 `shadowBlur` / `shadowColor` /
`filter` / `globalCompositeOperation` 装了 setter 探针，跑完整轮播放后断言
全部为 0（见 `test/verify.js`）。

> 说明：**余辉（afterglow）不是辉光**。余辉是同一像素随时间变暗（示波管荧光粉衰减），
> 辉光是亮度向四周扩散。前者保留，后者禁用。不想要拖尾的话把「余辉」拉到 0 即可，
> 此时每帧完全清屏。

## 采样率：不重采样

### 问题

`<audio>` + `AnalyserNode` 的常见写法**会重采样**。一个 Web Audio 图只能有一个采样率，
默认等于**设备**采样率（这台机器上是 48 kHz），媒体元素会把解码后的音频重采样进去。
所以 192 kHz 的 FLAC 会被降到 48 kHz，**24 kHz 以上的信息全部丢失**。

而这个文件确实有超声波内容：用 ffmpeg 解码后做频谱分析，高频段是实打实的信号，
不是抖动噪声（见下方实测）。

### 做法

**引擎采样率默认跟随音频文件本身。**

- 服务器版：从 `/api/tracks` 拿采样率（`server.js` 读文件头算出来的，不解码）
- 单文件版：直接从文件头部 256 KB 解析 WAV / FLAC / MP3 / M4A 的采样率
- 载入曲目时用 `new AudioContext({ sampleRate: 文件原生采样率 })` 重建引擎。
  因为 `createMediaElementSource()` 对同一个元素只能调用一次，所以 `<audio>`
  元素会连同上下文一起换新
- 顶栏常驻一个徽标随时显示状态：**`192 kHz 原生`**（绿色）或
  **`48 kHz ← 192 kHz 重采样`**（黄色警告）。设置面板里也可以手动指定引擎采样率

### 实测

用一份**独立的 ffmpeg 解码结果**作为基准，逐采样对比分析器拿到的时间窗：

| 引擎采样率 | 与 ffmpeg 基准的最大逐采样差 | 结论 |
|---|---|---|
| 192 kHz（原生） | `0` | **逐位相同**，没有重采样 |
| 48 kHz（强制跟随设备） | `6.1e-3`（残差 −42 dB） | 确实发生了重采样 |

超声波内容的去留（在 −21.7 dBFS 的乐句上测，避免测到静音段的噪声底）：

| | 30–88 kHz 相对 1–10 kHz |
|---|---|
| 192 kHz 原生 | **−26.8 dB PSD**（4950 个频点，真实内容） |
| 48 kHz | **该频段完全不存在**（超出 Nyquist，0 个频点） |

所以：**默认配置下，从文件到屏幕这条路径没有任何重采样。**

一点必须说清楚的边界：**送到扬声器**的那一路仍然会被系统重采样到设备采样率
（设备就跑 48 kHz），这无法避免，也听不出来。但它不影响画面 —— 分析器接在音频图里，
不在输出端。

代价是 192 kHz 引擎的 CPU 开销约为 48 kHz 的 4 倍。机器吃力的话，把「引擎采样率」
设成「跟随设备」即可，此时徽标会变黄提示正在重采样。

## 性能

### 实测

`node test/bench.js`，真实 Chromium，1280×800。单帧渲染耗时取 120 帧窗口里
**最快四分之一帧的均值**（为什么这么取见下文）：

| 配置 | 单帧渲染 | 相对基线 |
|---|---|---|
| 默认（窗口 4096） | 0.18 ms | — |
| 采样窗口 1024 | 0.08 ms | **−65%** |
| 采样窗口 8192 | 0.42 ms | +88% |
| 采样窗口 32768 | 1.49 ms | **+295%** |
| 关网格 | 0.14 ms | −19% |
| 渲染缩放 75% | 0.13 ms | −20% |
| 渲染缩放 50% | 0.22 ms | +12% |
| 引擎 48 kHz | 0.18 ms | −2% |
| **对照组（什么都不改）** | — | **−3%** |

结论很清楚：**开销几乎全在每帧要画多少条线段上，跟像素数关系不大。**
所以「渲染缩放」不是一个有效的优化杠杆 —— 50% 那行甚至略慢，因为同样的路径被挤进
更少的像素里，单位像素的覆盖反而更密。真正的杠杆是**采样窗口**。

对照组 −3% 说明这套测法的噪声底约 ±5%，低于这个幅度的差异不该采信
（比如「引擎 48 kHz −2%」就不该解读成有意义 —— 音频线程的开销本来也不在这个指标里）。

### 做了哪些优化

1. **渲染循环从约 13 遍扫描降到 2 遍。** 原来每帧要：扫峰值 → 映射到像素 → 算段长 →
   分档 → **每个亮度档再全扫一遍（9 遍）**。现在合并成一遍：映射、扫峰值、算段长、
   分档、把线段索引塞进对应档的列表全在一次遍历里完成；绘制时只遍历真正属于该档的
   线段。主线程 CPU 从 7.7% 降到约 4.5–5%。
2. **分析器只读需要的长度。** `fftSize` 跟着采样窗口走（窗口 4096 → fftSize 8192，
   而不是永远 32768），每帧少拷 4 倍数据，窗口 512 时少拷 32 倍。
3. **进度条 10 Hz 刷新**，不再每帧写三个 DOM 属性。
4. **自适应渲染缩放**（默认「自动」）：单帧中位数超过 10 ms 才降分辨率，恢复后再升回来。
   用**中位数**而不是均值，一次 GC 停顿不会触发降画质。
5. **性能模式**一键预设（快捷键 `O`）：窗口 2048 + 关网格 + 引擎跟随设备 + 75% 缩放，
   可随时关掉还原。这是给弱机准备的那个开关。
6. 顺带修掉两个 bug：暂停后动一下滑块画面就消失；重置设置不还原分析器长度
   （会把 4096 的窗口画在只有 1024 个采样的缓冲上）。

### 关于测量本身

`test/bench.js` 的数字有几个坑，都踩过并修掉了，记在这里免得误读：

- **不能用整机 CPU 占用率当结果。** 它会把别的进程（比如你同时在编译）算进来，
  毫无归属可言。现在整机占用只当「污染指示器」显示，超阈值就在那行标出来。
- **必须和紧邻的基线配对测量，且全程同一个浏览器会话。** 每个配置单开一个浏览器会带来
  ±0.5pp 的抖动，比要测的效果还大。
- **必须固定音频位置。** 渲染开销和音乐密度直接相关；不固定的话基线会在一轮里漂移 2 倍
  （这个真的发生过，一度让我以为机器降频了）。
- **`performance.now()` 被 Chrome 量化到 100 µs**，单帧数字没有意义。
  所以取 120 帧窗口里**最快四分之一**的均值：既恢复了亚量化精度，又天然免疫后台负载
  —— 后台负载只能让某些帧变慢，只可能往右加尾巴，动不了最快的那一批。

## 参数说明

| 参数 | 说明 |
|---|---|
| **X / Y 增益** | 每轴的电压放大倍数。调到 1.0 时 ±1.0 满量程刚好填满网格 |
| **X / Y 偏移** | 直流偏置，用来把偏离中心的图形拉回来 |
| **采样窗口** | 一帧画多少个采样点。小 = 只显示瞬时细节；大 = 一帧画出更完整的图形。括号里是对应的时长，随时长随采样率变化。**这是最有效的性能旋钮** |
| **引擎采样率** | `自动（匹配音频文件）` 为默认，保证不重采样；`跟随设备` 省 CPU 但会重采样；也可强制指定 44.1 / 48 / 96 / 192 / 384 kHz |
| **渲染缩放** | 画布的内部分辨率。只在填充率吃紧时（比如 4K / 高 DPI）有用，实测对单帧渲染时间影响很小 |
| **性能模式** | 一键预设：窗口 2048 + 关网格 + 引擎跟随设备 + 75% 缩放。快捷键 `O` |
| **亮度** | 电子束强度总倍数 |
| **线宽** | 束斑直径（设备像素） |
| **余辉** | 0% = 每帧全清（无拖尾）；100% = 长拖尾，用来累积出完整画面 |
| **速度消隐** | 见上文，强烈建议保持开启 |
| **相位锁定** | 在 X 轴上升过零点对齐窗口，周期性信号会更稳定；连续变化的音乐可以关掉 |
| **自动增益** | 按峰值自动调整整体增益（两轴用同一个系数，不会改变图形比例） |
| **光点** | 在束当前位置画一个亮点 |

## 目录结构

```
.
├── server.js                     # 零依赖 Node 服务器（静态 + 播放列表 API + Range 流式传输）
├── public/
│   ├── index.html                # 服务器版页面
│   ├── styles.css
│   └── app.js                    # 渲染内核 + 播放器（两个版本共用）
├── build-standalone.js           # 生成单文件版
├── oscilloscope-standalone.html  # ← 单文件自包含版（生成产物）
├── test/
│   ├── verify.js                 # 端到端验证（49 项）
│   ├── bench.js                  # 性能基准（含后台负载对照）
│   └── shots/                    # 验证时自动生成的截图
├── oscillofun.flac               # 测试音频 · 44.1 kHz / 16-bit / 立体声
└── primer-final.flac             # 测试音频 · 192 kHz / 24-bit / 立体声
```

`server.js` 只监听 `GET` / `HEAD`，仅提供 `public/` 下的静态文件与扫描到的音频，
并做了路径穿越防护。

### HTTP 接口

| 路由 | 说明 |
|---|---|
| `GET /` | 应用页面 |
| `GET /standalone` | 单文件版 |
| `GET /api/tracks` | 播放列表 JSON（含时长、采样率、位深、声道数） |
| `GET /api/health` | 健康检查 |
| `GET\|HEAD /media/<文件名>` | 音频流，支持 `Range`（206 / 416） |

`Range` 支持是必需的：`primer-final.flac` 有 270 MB，浏览器必须能只取需要的片段
才能拖动进度条。

## 验证

```bash
node test/verify.js
```

会自己拉起服务器并跑完整套检查，**HTTP 部分零依赖**，浏览器部分需要 Playwright
（检测不到会自动跳过并提示）：

- **HTTP**：播放列表、WAV / FLAC 文件头解析、Range（含 `bytes=-50` 后缀区间、
  越界 416）、`HEAD`、路径穿越拦截、方法限制
- **渲染**（真实 Chromium）：
  - 无控制台报错、画布正确随视口尺寸调整
  - **回扫线测试**：把一个合成信号塞进分析器 —— 慢速画一个正方形，再快速斜穿
    一条回扫线；正方形中心的像素只可能来自那条回扫线，于是直接量像素。
    结果：关闭消隐时中心 alpha = 250，开启后 alpha = **2**。
  - **辉光测试**：`shadowBlur` / `shadowColor` / `filter` / `lighter` 探针全为 0
  - `closePath` 调用次数为 0
  - 真实 WAV 走完整 Web Audio 链路播放、画面确实被绘制
  - 暂停后画面不消失（回归测试）
- **采样率**（真实 Chromium）：
  - 192 kHz FLAC → 引擎自动跑 192 kHz，顶栏显示「原生」
  - 超声波内容（30–88 kHz）确实进入了分析器；先断言捕获到的是**真实信号而非静音**，
    避免在噪声底上做测量
  - 反证：强制切到 48 kHz 后该频段超出 Nyquist，频点数为 0
  - 44.1 kHz WAV → 引擎跟着跑 44.1 kHz
- **单文件版**：`file://` 直接打开、零外部请求、选文件后用 blob URL 播放并出画面

## 常见问题

**Q：FLAC 播不了？**
浏览器需支持 FLAC（Chrome、Edge、Firefox、Safari 11+ 都可以）。若提示无法解码，
说明该浏览器缺解码器，可先用 `afconvert` / `ffmpeg` 转成 WAV。

**Q：为什么单文件版打开后是空的、也不能自动列出音频？**
`file://` 协议下浏览器禁止网页读取本地目录，这是安全限制。拖入文件即可。
想要自动列表就用 `node server.js`。

**Q：270 MB 的 FLAC 会不会卡？**
不会。播放走 `<audio>` 元素流式解码，服务器支持 Range，不会整文件读入内存，
也不需要 `decodeAudioData`（那样才会吃掉上 GB 内存）。

**Q：为什么默认要把音频引擎开到 192 kHz？不会更吃 CPU 吗？**
会，大约是 48 kHz 的 4 倍。但只有引擎和文件采样率一致时，分析器拿到的才是**文件
原始采样点**；否则文件 24 kHz 以上的内容会被直接丢掉。想省 CPU 就在设置里把
「引擎采样率」改成「跟随设备」，顶栏徽标会变黄提醒正在重采样。

**Q：画面太小 / 太大？**
调 X / Y 增益，或打开「自动增益」。注意两轴增益比例决定图形形状，
按需分别调整。

**Q：端口被占用？**
`node server.js -p 3000`，或直接回车让它自动往后找（最多 +10）。

**Q：余辉 0 时画面闪烁？**
窗口较小时确实会闪（每帧只画一个片段）。把余辉调到 40% 以上就能累积出完整画面。

## 技术要点

- **浮点时域数据**：用 `AnalyserNode.getFloatTimeDomainData()`（不是 8-bit 的
  `getByteTimeDomainData`），否则轨迹会有肉眼可见的 256 级台阶。
- **`fftSize = 32768`** 固定不变，窗口大小只是从中截取，切换窗口不用重建音频图。
- **`ChannelSplitterNode`** 把左右声道分开，喂给两个独立分析器。
- **零增益通路到 destination**：部分浏览器不会处理没有下游连接的分析器，接一个
  `gain = 0` 的节点保证它们一直被拉动，同时完全静音。
- **方形绘图区**：X/Y 用同一个像素/伏特系数，利萨如曲线才不会被拉成椭圆。
- **暂停时用快照**：`<audio>` 暂停后图里输出的是静音，所以暂停时必须继续用最后
  一帧捕获的采样来重绘，否则调个滑块画面就没了。
- **换采样率要连 `<audio>` 一起换**：`createMediaElementSource()` 对同一个元素
  只能调用一次，所以重建 AudioContext 时必须新建媒体元素，并重新挂监听、
  恢复播放位置。
