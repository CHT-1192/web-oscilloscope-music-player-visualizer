# 网页版示波器音乐播放 / 可视化器

左声道 → X 轴，右声道 → Y 轴。用电子束轨迹画出利萨如图形和示波器音乐里的矢量画面。

![预览](docs/preview.png)

> `oscillofun.flac` @ 20s —— **描边型**曲子的参数：窗口 1024、余辉 16%、增益 1.45。
> 余辉压低才看得到真正的束径，而不是拖尾叠加出来的一团糊。

**两个硬性要求：没有回扫线，没有辉光。** 两条都是量出来的，不是嘴上保证：

- **回扫线** —— 往分析器里塞一个合成信号（慢速画方块 + 快速斜穿一条回扫线），
  方块中心的像素只可能来自那条回扫线，于是直接量像素：关闭消隐 alpha=**250**，
  开启后 alpha=**2**。原理是速度消隐：亮度 ∝ 1/束速，比平均束速快过阈值（默认 10×，
  可在设置里调 1–15×，半档步进）的段落**直接不画**（只调暗没用 —— 余辉累加几十帧照样会浮出来）。

  上界为什么只到 15×：把余辉关掉、冻住同一帧，数每种阈值下画出来的像素（占 30× 的百分比）：

  | 阈值 | 1× | 3× | 5× | 10× | 12.5× | 15× | 20× | 30× |
  |---|---|---|---|---|---|---|---|---|
  | Oscillofun（画线） | 69.8% | 87.5% | 92.6% | 98.2% | 98.5% | 98.5% | 99.2% | 100% |
  | Primer（画面） | 31.6% | 69.2% | 71.8% | 80.0% | 86.0% | 93.0% | 100% | 100% |

  曲线在 10–15× 就基本躺平了，剩下的是两条曲线尾巴上那薄薄一层「不算慢也不算快的」
  线段 —— 想一个都不消，那是「速度消隐」开关的事，不该让滑块去干。原来给到 30× 是假量程。
  下界 1× 则确实有用：Primer 会掉到三分之一，只剩慢笔画，是一种能用的骨架效果，不是坏掉。
- **辉光** —— 不用 `shadowBlur`、不用叠加混合、不用模糊滤镜；余辉只做减法衰减，像素只会
  变暗，不会把亮度渗给邻居。测试里给这几个 API 装了 setter 探针，跑完整轮播放后断言全为 0。

  亮度本身现在是**能量模型**（WebGL2）：每帧把 `1/束速` 的曝光**加性**写进一张浮点累积
  缓冲，再按 `exp(-dt/τ)` 衰减，最后用 `1−exp(−E/E₀)` 做饱和映射显示。这正是真实示波器的
  做法，也顺手解决了老 8 位路径的三个问题：亮度 ∝ 1/v 不再需要分档、不存在量化地板、
  饱和是渐进的而不是硬裁。

  加性沉积**不会**变成辉光：能量只落在束流真正打到的像素上，只被光斑自己的高斯轮廓摊开
  （而轮廓在 3σ 处**严格截到 0**），从不把亮度渗给邻居。

  束流的光斑**宽度是恒定的**：真实管子上它由束流和聚焦决定，跟束流这一瞬间走多快无关
  （随剂量变宽试过了，见「光晕」一节）。唯一会让画面发光的，是设置里那个**默认关闭**的
  「光晕」滑块，也就是 **halation 云**：荧光粉发出的光在粉层和玻璃里横向散射，所以整个
  图形周围浮着一层宽而暗的雾。它加在**色调映射之后**，作用在**已经发出来的、有界的光**
  上。开关关掉时这一整条路径**一行代码都不跑**，画面和以前逐像素一致。

  没有 WebGL2 或没有浮点渲染目标时自动退回原来的 Canvas-2D 路径（`?renderer=2d` 可强制，
  测试对**两条路径各跑一遍**）。

## 操作

拖音频文件进窗口即可播放。

![界面](docs/ui.png)

布局的原则是**画布不动，只有绘图区让位**：

- 画布（背景、网格、画布本身）永远占满窗口，开关面板**不会改变它的尺寸或位置**。
- 面板是浮层，落在正方形绘图区两侧的留白里。正方形居中，所以宽屏下两侧留白很宽
  —— 1600×900 时两侧各有约 400px，一个 330px 的面板整个塞得进去，**绘图区一动不动**。
- 只有当留白真的塞不下时（比如小窗口双开），绘图区才缩小，而且保持居中，不会被推向
  一边。窄屏（≤900px）没有余量，退回浮层覆盖。

切面板时会用 `layout()` 重新算绘图区，配合前面说的图层跨缩放保留，画面不会丢。

| 键 | 作用 | 键 | 作用 |
|---|---|---|---|
| `空格` | 播放 / 暂停 | `D` | 演示信号（不需要音频文件） |
| `←` `→` | 后退 / 前进 5 秒 | `F` / `S` | 全屏 / 存 PNG |
| `↑` `↓` | 音量 | `L` / `P` | 播放列表 / 显示设置 |
| `,` `.` | 上一首 / 下一首 | `O` | 性能模式开关 |
| `L` | **输出帧日志到控制台**（见下） | | |
| `B` `T` `G` | 速度消隐 / 相位锁定 / 网格 | `R` | 恢复默认设置 |

### 参数跟着曲子走，没有通用最优

描边型和填充型的要求正好相反，所以**默认值取两者的中点**：

| | 采样窗口 | 余辉 | 线宽 | 亮度 | |
|---|---|---|---|---|---|
| **默认** | **2048** | **24%** | **1.75** | 0.9 | 下面两行的中点；也不是随便挑的，见下 |
| **描边型** · `oscillofun.flac` | **1024** | **16%** | 1.15 | **3.5** | 就是上面那张预览图 |
| **填充型** · `primer-final.flac` | **4096** | **32%** | **2.3** | **0.1** | ↓ |

第五列「亮度」是曝光量，**能量模型下它必须每套配方各给一个**：细线的能量摊在更窄的
面积上、峰值更低，密集图形的重叠又会不断累加，所以同一个数字不可能同时服务两者 ——
实测要达到各自在 Canvas 路径上的观感，描边需要 3.5、填充需要 0.1（默认 0.9 则是标定过
的中间值：在最密段落上过曝 0.89%）。两条预设同时带一份 **Canvas 路径专用的曝光**，
所以在没有 WebGL2 的机器上套用同一个预设，观感也对得上（描边 72 / 83，填充 54 / 75）。

### 一段亮一段不亮：亮度就是 1/束速

真实示波器上一条笔画常常是**虚的** —— 慢的地方亮成一小段，快的地方几乎看不见。
那就是 1/v 本身：沉积的电荷 ∝ 停留时间，而停留时间 ∝ 1/束速。

这里有一个被修掉的坑：分母里曾经有个 `图宽 × 0.0015`（600 px 的图上约 0.9 px）的
"防除零地板"，它比很多段落的实际步长还大，于是把整条 1/v 曲线压平了 ——
**静止的束流只有平均速度的 2 倍亮，而它应该是几十倍**。改成纯数值地板（`2e-5`）后，
实测：匀速扫过 ×1.0，静止束流 ×20（上界来自参考束速本身的地板 `图宽 × 0.0004`）。

看不见虚线还有第二个原因，那个不是 bug：**一个窗口里图形要被画好几遍**。
2048 采样在 44.1 kHz 下是 46 ms，音乐里同样的图形已经重复了很多次，
亮段和暗段落在同一批像素上互相叠加，就糊成一张均匀的网。想看虚线就换配方：

| | 采样窗口 | 余辉 | 亮度 | 覆盖率 | 亮暗比 p90/p50 |
|---|---|---|---|---|---|
| 默认 | 2048 | 24% | 0.9 | 11.6% | 2.1 |
| **虚线**（参考照片那种） | **512** | **0%** | **0.45** | **2.3%** | **3.1** |

同一段 Oscillofun @20s、同一台机器上量的。覆盖率差 5 倍，就是"一张亮网"和
"几根细线、明暗分明"的区别；配 1.15 线宽和低余辉更接近照片里的观感。

8 位回退路径没有累加缓冲，只有十级 alpha 阶梯，所以它把同一个剂量过一条饱和曲线
（形状就是那条色调映射）再落到阶梯上，并把阶梯整体乘 0.8 保持原来的工作点 ——
它的亮暗比仍然不如能量路径，这是 8 位阶梯的极限，README 不打算假装它一样。

「中点」是取舍，不是最优点 —— 最优点确实因曲而异，那才需要预设。但默认值**不能落在
坏区间**，这个是能量出来的。把窗口 × 余辉扫一遍，每格重新加载、播 9 秒，只统计绘图区里
两个数：**覆盖率**（亮起的像素占比）和**过曝率**（alpha ≥ 250 的占亮起像素的比例）。
Oscillofun @20s，增益 1.0、亮度 0.9、网格关：

| 余辉 | 0 | 8 | 16 | **24** | 32 | 48 | 62 |
|---|---|---|---|---|---|---|---|
| 1024 · 覆盖 | 3.2 | 4.2 | 5.1 | 6.5 | 7.4 | 10.4 | 14.9 |
| 1024 · 过曝 | 0.31 | 0.32 | 0.35 | 0.22 | 0.30 | 0.35 | **1.45** |
| 2048 · 覆盖 | 5.4 | 6.2 | 7.1 | 7.9 | 9.0 | 11.9 | 16.4 |
| 2048 · 过曝 | 0.53 | 0.49 | 0.55 | **0.66** | 0.90 | 1.19 | **5.25** |
| 4096 · 覆盖 | 8.1 | 8.7 | 9.4 | 9.8 | 10.8 | 14.3 | 17.9 |
| 4096 · 过曝 | 1.50 | 1.82 | 2.02 | 2.61 | 3.17 | 4.70 | **12.82** |

（单位 %）

- **旧默认的 62% 落在过曝区**：5–13% 的笔画已经顶到 255，也就是糊成一片、分不出笔画了 ——
  不是"更浓"，是信息没了。所以那个数字不只是随手写的，是随手写还写错了地方。
- **2048 是过曝率还能压住的最大窗口**：4096 在任何余辉下都 ≥1.5%（一帧里线段本身就自重叠），
  1024 到 48% 还行、62% 也破 1%。
- **24% 在安全线内还留了余量**（0.66%），32% 也还行（0.90%），48% 已经到边。
- 覆盖率随余辉单调上升、没有拐点，所以"最优"无从谈起 —— 这一点和「每首曲子参数不同」
  本来就是同一件事。

测量口径：只在一条画线型曲子上量的（填充型的球体在默认增益下覆盖太小，过曝恒为 0，
约束落不到它身上）；余辉越高，9 秒内越到不了稳态，所以 62% 那一列的真实过曝只会比表里更严重。

![填充型：primer-final.flac @ 2:43 —— 棋盘格球体，整曲的核心符号](docs/preview-primer.png)

![同一首曲子 @ 1:12 —— 放射状的「穿梭」效果](docs/preview-warp.png)

判断方法：**这首曲子在画线，还是在画面？**

- **画线**的（Oscillofun）压低余辉、缩小窗口，让真正的束径露出来；
- **画面**的（Primer）反过来 —— 用窗口和余辉把面积堆实，线宽也得跟上。

回扫阈值也是按曲调参的：不同曲子的回扫速度不一样，阈值太大回扫消不干净，太小又会
削到有效笔画（默认 10×，范围 1–15×，半档步进）。它跟「速度消隐」是配套的，开关关掉时
这个滑块会置灰。

同一段 Primer 换参数就能看出这不是玄学：描边配方（1024/16%）会让球体碎成几段
轮廓，余辉拉到 62% 又会堆积过头、边缘飞出杂线；只有 24–32% 这一档是干净的实心球体 ——
默认的 24% 正好落在这一档里。

### 预设：一键切配方，两种模式

上面那两套配方不是让你每次手动拖的，它们就在设置面板顶部：

```
预设  PRESETS      [ 自动 · 按曲记忆 | 手动 ]
[默认] [描边] [填充] [我的描边 ×]
oscillofun.flac — 描边 · 已微调
[保存当前] [导出] [导入]
```

**内置三档**：`默认`（2048 / 24% / 1.75 线宽 —— 上表第一行）、`描边`（1024 / 16% / 1.15，
给 Oscillofun）、`填充`（4096 / 32% / 2.3 线宽，给 Primer）。后两档的三项参数在代码里是
**写全的**，不从默认值继承 —— 否则改一次默认值，预设就会悄悄跟自己的文档对不上。

**两种模式并存，不冲突**：

- **自动 · 按曲记忆（默认）**：切歌自动套用这首曲子上次用的设置。改了什么就记什么，
  所以"上次调到哪"不会丢，也不用每次切回去再拖一遍。
- **手动**：切歌不动设置，只有点预设才变。想拿一套参数横扫整个列表时用这个。

两种模式下**都会记录**每首曲子的设置，手动模式只是不自动套用 —— 所以中途换模式不会
丢东西。第一次播一首新曲子时沿用当前设置（不跳变），之后它就有了自己的记忆。

**自定义**：拖出满意的一套，点「保存当前」起个名字。同名再保存就是覆盖，双击预设名
可以改名，`×` 删（要点两下 —— 删预设没有后悔药）。自定义预设存在浏览器本地，刷新、
关掉再开都还在（`localStorage`，file:// 下被禁用时就只在本次会话有效，不报错）。

**导出 / 导入**：自定义预设能序列化成一段 JSON 文本，贴给谁都能用。导入会**校验**：
只认识的键、只接受滑块表达得了的范围 —— 别人给你一个 `blankRatio: 999`，落地就是 15×，
滑块和读数不会互相撒谎；名字撞车自动让位成「xxx 2」；不是 JSON 就原样不动、只弹一句提示。

**预设不包含**「引擎采样率」和「渲染倍率」：这两项描述的是你**这台机器**，不是画面。
预设是要发给别人的，一个会偷偷把别人音频引擎切到 192 kHz 的预设是 bug 不是功能。

另有两个默认关闭、只在一条渲染路径上有效的滑块（另一条路径上会**置灰**，并说明原因 ——
一个拖得动却什么都不改的滑块是在撒谎）：

- **残留**：修的是**8 位路径**上的一个量化坑。`destination-out` 是 `n ← n×(1-a)`，8 位画布
  四舍五入，于是 **n ≤ 1/(2a) 全是死点，永远降不下去**。所以余辉拉高不是"留得更久"，
  而是**残影更亮**（100% 时地板是 alpha 15，整片扫过的区域永久留下约 16% 的淡痕）。
  这个滑块控制擦除力度：0 = 定期彻底擦掉（默认，无残留），越大留得越明显。
  **能量路径上这个滑块是无效的**（所以那一行在 WebGL 下置灰）—— 浮点缓冲按 `exp(-dt/τ)`
  衰减，没有最小可表示值，也就没有地板可擦。测试直接量了这件事：滑块拉到 100% 和 0%，
  结果必须一致。
- **光晕**：**只在能量路径上有**（Canvas 路径是恒定线宽、也没有浮点缓冲，所以那边置灰）。
  它是一层 **halation 云**：荧光粉发出的光在粉层和玻璃里横向散射，于是整个图形被一层
  宽而暗的雾包住 —— 参考照片 2、3 里那圈绿光就是它，照片里的亮球也是它（一个亮点被散射
  糊成球），**不是**光斑变宽。

  它加在**色调映射之后**，输入是**已经发出来的、有界的光**，输出永远不超过自己的幅度上限。
  取样用三个尺度：mip 1（2 px 格，比一个 CSS 像素还细，看不出格子）、mip 4 与 mip 6 先各做
  一次 13 点 tent 模糊再取。**模糊这一步不是可选项**：对粗层级做单次双线性取样会把它的
  纹素格子放大，细笔画就是"一串小点"。

  因为它是屏幕亮度的**卷积**，浓密图形周围非常明显、单根细线周围几乎看不见 —— 这不是
  需要调掉的缺陷，这正好解释了那几张参考照片为什么彼此差那么多。实测：合成细线径向剖面
  `10/18/28/40/55/75/100/130 px → 12/9/5/3/1/1/0/0`（单调、最大单步落差 4，没有断崖），
  而浓密图形上（同一条合成曲线）画面平均 alpha 从 2.5 涨到 4.7；**光晕 0 时 10 px 和 28 px
  处严格是 0**，和以前逐像素一致。合成信号上光晕 0→100：亮起像素 26509→93752。

  > **踩过的两个坑，都值得记着。**
  > ① 第一版把光晕做成了**光斑变宽**，也就是加在能量缓冲里。那是错的层次：停留一处会
  > 沉积出饱和映射所需能量的一万倍，光晕项自己也被推到饱和、一路平到它的截断半径，
  > 渲染出来是一块**硬边圆饼**（255 到边缘然后什么都没有），而照片里是渐变的球。
  > ② 第二版让**光斑宽度随剂量变**。物理上就错了（光斑宽度由束流和聚焦决定，不是书写
  > 速度），画面上更糟：相邻采样点的剂量天差地别，于是每一段都成了自己的一个小圆盘，
  > 整条笔画变成**一串小点**。
  > 顺带：亮度用的是**沿路径平滑过的** 1/束速（磷酸粉在一个光斑宽度上做积分），
  > 否则采样级的抖动同样会把笔画点阵化 —— 虚线应该是"一段一段"，不是"一点一点"。

### 卡顿就看日志,不用录 profiler

按 **`L`**（或控制台里 `__scope.perf()`，`__scope.perf(60)` 只看最近 60 秒）会往控制台打一段
纯文本帧日志,可以直接复制:

```
帧日志:360.0s / 20578 帧
  中位 16.68 ms (60.0 fps) · p90 17.10 · p99 17.59 · p99.9 119.53 · 最差 480.2 ms
  1% low 21.1 fps · 0.1% low 4.5 fps
  超 20/33/50 ms 的帧:77 / 58 / 44
  最差的几帧:
    480.2 ms (2.1 fps) · 0 seg · 光晕开 · 该帧前刚 resize
    ...
  事件(负号 = 多少秒前):
    -1.2s  音频 waiting
    -3.4s  resize 3024×1964 @2x
```

它记的是**帧间隔**（不是帧内工作时间），并且给最差的那几帧记下当时的**线段数、光晕开关、
是否刚 resize** —— 所以"这一下是我的渲染、还是合成器/系统"当场就能分辨。媒体事件
（playing/pause/waiting/stalled/error）也打在同一条时间线上,"没声"那一刻前后发生了什么
一目了然。窗口是最近 2048 帧。

### 手性：X / Y 反向

约定是 **X = 左声道、Y = 右声道，Y 的正方向朝上**（示波器的分划板就是这么画的）。但
曲子是按某个手性制作的，参考视频里那台机器的 Y 输入也可能正好反接 —— 于是同一首歌在
别人那里转 180° 才对得上。这不是 bug，是**素材的属性**，所以开关在「开关」那一组里：
**Y 反向** / **X 反向**，各自独立，跟着每首曲子的记忆和预设一起走。

翻转时**增益读数带负号**（`1.00 → -1.00`）：读数要显示映射真正用的值，否则就是"读数
在撒谎"。测试量了两件事 —— 翻转前后墨迹从中心下方 180 px 跑到上方 180 px，以及读数
确实变成 `-1.00`。

余辉的累积会**跨曲目保留**，也会在窗口缩放 / 全屏切换后按比例保留
（重设 `canvas.width` 会清空位图，所以要手动搬过去，否则改一下窗口大小残影就没了）。

## 两个不那么显然的设计

**① 采样率不重采样。** Web Audio 图只有一个采样率，默认等于**设备**采样率
（一般 48 kHz），媒体元素会把音频重采样进去 —— 192 kHz 的文件就这么被砍到 24 kHz
以下。所以本项目默认让引擎跟随音频文件本身的采样率，分析器拿到的是**文件原始采样点**：
拿一份独立的 ffmpeg 解码结果逐采样比对，最大差值 `0`（逐位相同）；强制切到 48 kHz
后同段残差 −42 dB。顶栏徽标随时显示当前是「原生」还是「重采样」。

**② 性能瓶颈不在像素上。** 单帧开销几乎全在**要画多少条线段**，跟分辨率关系不大。
渲染循环用一遍扫描同时完成映射、扫峰值、算段长、分亮度档，而不是每个亮度档再全扫一遍。
实测：窗口 32768 → 1024 把单帧从 **1.49 ms 降到 0.08 ms**；「渲染缩放 50%」
反而略慢（同样的路径挤进更少的像素，单位像素覆盖更密）。弱机按 `O` 开性能模式。

能量路径每帧是 GPU 上的三次绘制（衰减、沉积、映射）加一次 blit；CPU 只上传每段 5 个 float。
用 CPU 做同一件事的代价实测过：全缓冲 float 衰减 + 映射到 8 位，900×900 朴素 1.70 ms/帧、
查表优化后 0.97 ms，512×512 只要 0.26 ms —— 这也是为什么它交给 GPU。

其余细节都在代码里：`public/js/` 下的各个模块和 `test/bench.js` 顶部都有大段注释说明。

```
public/js/presets.js            内置与自定义预设、两种模式、导出导入          ← core apply
public/js/playlist.js           曲目列表、文件选择、演示信号、播放控制        ← core audio render presets

public/index.html  styles.css

docs/                           预览图
test/verify.js                  157 项端到端验证
test/bench.js                   性能基准
LICENSE                         Apache License 2.0（取自 apache.org 原文，仅填入版权行）
```

依赖是**分层单向**的（箭头只往下指，无环）：`core → audio → render → apply → presets → playlist → ui → main`。
每个模块只通过命名空间调用（`audio.isLive()`）或顶部解构出来的别名引用依赖，没有跨模块的裸变量 —— 后者在
一个大文件里永远不会暴露，拆开才看得见。

服务器版直接按 ES 模块加载；单文件版由 `build-standalone.js` 把同一批源码内联成一个 `<script>`。
内联器只认一种极小的方言（`import * as ns from './x.js'` + `export function/const/{...}`），
其余形式（`export default`、`export let`、具名 import、动态 `import()`、**import 环**、指向不存在导出的别名）
一律**报错退出**而不猜 —— 其中 `export let` 在真 ESM 里是活绑定、内联后会变成快照，与其悄悄编错不如编译不过。

**音频文件不进版本库**（两个测试文件合计约 300 MB），见 `.gitignore`。
把任意音频丢进项目根目录即可，服务器会自动扫到。

## 几句实话

- **单文件版在 `file://` 下不能自动列目录** —— 浏览器安全限制，拖进去或点「选择文件」。
- **FLAC 播不了**说明该浏览器缺解码器，先转 WAV。
- **ALAC / AIFF / AIFF-C / CAF 在 Chrome / Chromium 里播不了** —— 不是文件的问题，是这些
  浏览器**没有对应解码器**：`canPlayType('audio/mp4; codecs="alac"')` 和 `canPlayType('audio/aiff')`
  都返回**空字符串**，元素报 `MediaError 4`。Safari 都能放。界面会直接报出是哪种格式，
  不含糊成一句"无法解码"。
- **采样率是从文件头读的，不靠解码**。覆盖：WAV、FLAC、MP4 系列（`m4a`：AAC / ALAC）、
  AIFF / AIFF-C / CAF、Ogg（Vorbis / Opus）、MP3。几处不那么显然的地方：

  - **MP4**：采样率在 box 树里，而 `moov` 常常在**文件末尾**（mdat 在前，ffmpeg 的默认写法），
    所以要补读一段尾部；ALAC 更进一步——通用 sample entry 的采样率是 **16.16 定点，装不下
    65535 Hz 以上**，真值在那个 36 字节的 codec box 里。
  - **AIFF**：采样率是 **80 位 IEEE 扩展浮点**（1 符号 + 15 指数 + 64 位尾数），不是整数。
    AIFF-C（`.aifc`）只是多一个压缩标记 —— ffmpeg 把 `pcm_s16le` 写进去时标记是 `sowt`。
  - **Ogg**：时长不在任何头部里，是**最后一页的 granule position**，所以它也要读尾部。
    Opus 一律报 48 kHz —— 它解码出来就是 48 kHz，分析器看到的就是这个。
  - **MP3**：只报采样率和声道。时长要么扫全部帧、要么读 Xing 头，**报错不如不报**。
  - **仍未解析**：裸 `.aac`（ADTS）和 `.webm / .weba`（EBML）。这两种会退回设备采样率，
    也就是**会被重采样** —— 是已知缺口，不是没意识到。
- 270 MB 的 FLAC 不会卡：走 `<audio>` 流式解码 + 服务器 Range，不整文件进内存
  （`decodeAudioData` 才会吃掉上 GB）。
- 「余辉」拉到 0 会闪（每帧全清，只画一个片段），40% 以上才累积得出完整画面。
